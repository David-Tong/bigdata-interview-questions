# 外部归并排序

## 问题

在一台内存为 32 GB 的机器上，按照某个可比较的字段对 1 TB 数据进行全局排序。数据不能一次全部装入内存。

外部归并排序分为两个阶段：生成有序段（run generation）和多路归并（multi-way merge）。

延伸阅读：[从外部归并排序到 Hadoop MapReduce](./external-sort-and-mapreduce.md)。

## 第一阶段：生成有序段

顺序读取原始文件，逐批在内存中排序，并将每批结果写入一个临时文件，称为有序段（run）。读取时应以完整记录为单位，不能在块边界截断记录。

假设输入是一个 1 TB 的文件，打开这个文件并不意味着把它全部读入内存。程序从中读取一批记录，在内存中保存并排序这些记录，然后将排序结果写入一个 run；接着继续读取下一批，重复上述过程。生成 run 时还需要打开相应的输出文件。

**有序段的大小取决于内存中能够同时加载并排序的数据量**，而不是由 32 GB 内存直接决定。记录解析后的占用、排序辅助空间、缓冲区和运行时开销都会影响实际批次大小；具体能处理多少，需要根据数据格式和实际内存使用情况确定，并为系统预留余量。各批次及其输出文件也不一定完全等大。

例如，假设经过评估每批能处理约 16 GB 的原始数据，且输出数据大小与输入相近，则 1 TB 数据约产生 64 个有序段：

```text
原始文件 -> 读取一批 -> 内存排序 -> run0
         -> 读取一批 -> 内存排序 -> run1
         -> ...
         -> 读取一批 -> 内存排序 -> run63
```

这里的 16 GB 指**每批读入内存并参与排序的原始数据量**，并非对有序段大小的保证。写出约 16 GB 的文件本身不要求有 16 GB 内存，可以通过缓冲区分批写入；内存主要用于保存当前批次的待排序数据。

每个 run 内部有序，但不同 run 之间尚未全局有序。

## 第二阶段：多路归并

同时打开有序段，为每个输入文件分配缓冲区，并为输出文件分配缓冲区。例如，64 个 run 每个使用 4 MB 输入缓冲区，共需 256 MB；还需留出堆、当前记录、输出缓冲区和运行时所需的内存。

使用最小堆维护每个 run 当前尚未输出的最小记录：

1. 从每个非空 run 读取一条记录，连同其来源放入最小堆。
2. 取出堆顶记录并追加到输出缓冲区；缓冲区达到设定容量时，将其中的数据写入输出文件，然后清空缓冲区以便继续使用。
3. 从该记录所属的 run 读取下一条记录，若存在则放入堆。
4. 重复步骤 2 和 3，直到堆为空；将输出缓冲区中剩余的未写入数据写入文件，并关闭输出文件。

输出文件约为 1 TB，但数据是在归并过程中分批写入磁盘的，不会全部保存在输出缓冲区里。例如，使用 4 MB 输出缓冲区时，缓冲区写满便写出并复用；归并结束时只需写出最后不足 4 MB 的剩余数据。实际缓冲区大小应考虑内存预算和 I/O 性能。

堆中最多有 64 条记录。对于 N 条记录和 K 个 run，归并的时间复杂度为 O(N log K)；当 K 为 64 时，log₂ 64 = 6。

如果可用内存或系统允许打开的文件数不足以同时归并所有 run，可以分批归并成新的有序段，再进行后续轮次，直到得到一个最终文件。

## I/O 和空间开销

假设临时数据和输出数据的大小均约为 1 TB，且所有 run 可以在一轮中归并：

| 阶段       | 读取          | 写入          |
| ---------- | ------------- | ------------- |
| 生成有序段 | 1 TB 原始数据 | 1 TB 临时数据 |
| 多路归并   | 1 TB 临时数据 | 1 TB 最终结果 |
| 合计       | 2 TB          | 2 TB          |

因此总 I/O 量约为 **4 TB**。每增加一轮完整归并，大约再增加 1 TB 读取和 1 TB 写入；实际开销取决于中间文件大小及归并方式。

如果保留原始文件，且在最终结果完成前保留所有输入 run，最坏情况下需要同时容纳原始数据、临时数据和最终结果，约 **3 TB 磁盘空间**，另留必要的余量。多轮归并时还需考虑中间文件的空间和清理时机。

## 实现时的注意事项

- 所有阶段必须使用一致的排序键和比较规则，包括升降序、空值处理及相同键的顺序。
- 如需稳定排序，可将记录在原始输入中的位置作为次级键。
- 检查磁盘空间、文件句柄限制以及读写错误；最终输出完成并校验后，再清理仍需保留的临时文件。

## Linux 的缓存与缓冲

这里重点讨论**内核管理的内存**。文件系统负责组织文件和处理文件操作，内核页缓存则用于缓存文件数据；两者有关联，但不是同一个概念。程序或 Python 库还可以在用户态另设缓冲区，那是独立于内核缓存的一层。

对于普通的缓冲文件 I/O，数据通常经过以下路径：

```text
读取：存储设备 -> 内核页缓存 -> 程序输入缓冲区 -> 排序程序
写入：排序程序 -> 程序输出缓冲区 -> 内核页缓存 -> 存储设备
```

### Cache 和 buffer 的区别

- **Cache（缓存）**强调保留数据以便后续复用。例如，内核页缓存保存文件数据，目录项和 inode 缓存保存文件系统元数据。
- **Buffer（缓冲）**强调在传输或写入期间暂存数据，以协调处理速度。例如，Linux 中与块设备及文件系统块相关的缓冲机制。

这两个概念并非完全独立的两块内存：页缓存既能保存读取过的文件数据，也能暂存尚未写回的修改。因此，不能简单地说 cache 只用于读取、buffer 只用于写入。`/proc/meminfo` 中的 `Buffers` 和 `Cached` 是特定的内核统计字段，不是对所有缓冲和缓存的通用分类。

### 普通文件如何读取和写入

- **读取**：内核先检查需要的文件数据是否已在页缓存中。如果命中，就把数据复制给程序；如果未命中，内核通过文件系统从存储设备读取，再返回给程序。内核也可能进行预读。
- **写入**：内核通常先将程序提交的数据写入页缓存，使相应缓存页成为**脏页**；内核之后安排写回存储设备。脏数据过多时，写入进程也可能被迫等待。

页缓存主要按文件和文件内的偏移关联，不是按进程或文件描述符各存一份；多个进程访问同一文件的相同数据时通常可以共享缓存。它是全系统管理的资源，在容器或受 cgroup 限制的环境中也可能受到相应的内存限制。

### 文件句柄中记录了什么

程序打开文件后，操作系统怎么知道它在读哪个文件、读到了哪里？这里要区分三个对象：**文件描述符、打开文件描述和底层文件**。它们有关联，但记录的信息不同。

#### 第一层：文件描述符——进程用来访问文件的编号

在这里，“文件句柄”指 Linux 的**文件描述符**（file descriptor，简称 fd）。例如，`open()` 可能返回整数 `3`，程序随后用 `read(3, ...)` 读取文件。

数字 `3` 本身并不保存文件内容或当前读取位置。内核为进程维护一张文件描述符表：用 fd 找到对应表项，再由表项找到打开文件描述。

描述符表项还保存**描述符标志**，例如 `FD_CLOEXEC`：开启该标志后，进程成功执行 `exec()` 时会关闭该 fd。不同进程都有各自的描述符表，因此两个进程的 fd 3 不一定指向同一个文件。

#### 第二层：打开文件描述——一次打开的状态

**打开文件描述**（open file description）是内核维护的对象，记录这次打开的状态，主要包括：

- **当前文件偏移**：普通顺序读取或写入时，从文件的哪个字节位置开始。
- **访问模式**：例如只读、只写或读写。
- **文件状态标志**：例如追加写入的 `O_APPEND` 和非阻塞模式的 `O_NONBLOCK`。
- **关联的底层文件**：使内核能够找到实际操作的文件对象。

对普通文件，`read()` 成功返回数据后，偏移通常按实际读取的字节数前移；`write()` 同理。`pread()` 和 `pwrite()` 则使用调用时指定的偏移，不改变打开文件描述中的当前偏移。

#### 第三层：底层文件和内核页缓存

底层文件由文件系统管理，有自己的内容和元数据，例如文件大小、权限和 inode 信息。内核页缓存按文件及文件内的偏移关联文件数据，用于缓存读取过的数据或暂存待写回的数据。

多个打开文件描述可以关联同一个底层文件，也可以访问同一份页缓存；但它们不一定共享读取位置。**页缓存不是文件描述符表项，也不是打开文件描述中单独保存的一份文件数据。**

例如，同一个进程分别打开文件 X 两次，得到两个 fd：

```text
进程的描述符表             内核中的打开文件描述             底层文件
fd 3  ----------------->  A：偏移 0、只读  ----\
                                                > 文件 X 及其页缓存
fd 4  ----------------->  B：偏移 0、只读  ----/
```

#### 读取例子：两次打开与 `dup()`

假设文件 `X` 的内容是字节 `abcdefghij`。进程调用 `open()` 两次，分别得到 fd 3 和 fd 4（数字仅为示例，实际由内核分配）：

偏移表示下一次顺序读取的位置，按字节计数；开始时两个打开文件描述的偏移都是 0。下面假设每次 `read()` 都成功返回请求的字节数：

| 操作            | 返回  | A 的偏移（fd 3） | B 的偏移（fd 4） |
| --------------- | ----- | ---------------- | ---------------- |
| 刚打开          | —     | 0                | 0                |
| `read(fd 3, 3)` | `abc` | 3                | 0                |
| `read(fd 4, 2)` | `ab`  | 3                | 2                |
| `read(fd 3, 2)` | `de`  | 5                | 2                |

fd 3 已读到偏移 5，fd 4 却仍从自己的偏移读取：两次 `open()` 创建了两个独立的打开文件描述。若文件数据仍在页缓存中，两次读取可以复用缓存，但缓存也可能被回收。

如果接着执行 `fd 5 = dup(fd 3)`，情况就不同了。`dup()` 新建描述符表项，但**不新建打开文件描述**；fd 3 和 fd 5 都指向 A：

```text
fd 3  ----\
            > A：偏移 5，O_RDONLY ----\
fd 5  ----/                            > 文件 X
fd 4  ------> B：偏移 2，O_RDONLY ----/
```

| 操作                | 返回 | A 的偏移（fd 3、fd 5 共享） | B 的偏移（fd 4） |
| ------------------- | ---- | --------------------------- | ---------------- |
| 复制后              | —    | 5                           | 2                |
| `read(fd 5, 2)`     | `fg` | 7                           | 2                |
| `read(fd 3, 1)`     | `h`  | 8                           | 2                |
| `pread(fd 5, 2, 0)` | `ab` | 8                           | 2                |

`pread()` 从指定的偏移 0 读取，不修改共享的当前位置。关闭 fd 3 后，fd 5 仍指向 A，可以继续从偏移 8 顺序读取；当不再有对 A 的引用时，内核才释放这个打开文件描述。fd 3 和 fd 5 共享 A 的偏移及文件状态标志，但各自有描述符标志。

#### 进程之间如何共享

如果进程在打开文件后调用 `fork()`，子进程会继承对应的描述符。父子进程有各自的描述符表，但继承来的表项指向同一个打开文件描述：

```text
父进程 fd 3  ----\
                   > 打开文件描述 A：共享偏移 ----> 文件 X 和页缓存
子进程 fd 3  ----/
```

父进程通过 fd 3 读取后，子进程下一次顺序读取会使用更新后的共享偏移；两个进程并发读取时，实际由谁先读取取决于执行顺序。与此不同，如果子进程再调用一次 `open()`，新 fd 对应新的打开文件描述和独立偏移，但仍可共享文件 X 的页缓存。

概括来说：

| 操作                      | 描述符表项       | 打开文件描述和偏移 | 底层文件及页缓存     |
| ------------------------- | ---------------- | ------------------ | -------------------- |
| 同一文件调用两次 `open()` | 两个             | 独立               | 相同文件，可共享缓存 |
| `dup()` 复制 fd           | 两个             | 共享               | 相同                 |
| `fork()` 继承 fd          | 分别属于父子进程 | 共享               | 相同                 |

外部归并时，通常每个 run 打开一个 fd，分别维护该 run 的读取位置；输出文件也需要 fd。打开文件数量受到进程及系统限制，run 太多时可能遇到 `EMFILE` 等错误，应限制归并路数或分多轮归并。

可以在 Linux 上观察某个进程的描述符：

```bash
ls -l /proc/<pid>/fd
cat /proc/<pid>/fdinfo/<fd>
ulimit -n
```

将 `<pid>` 和 `<fd>` 替换为实际数字。`fdinfo` 对普通文件通常显示当前偏移 `pos`、打开标志 `flags` 等信息；内容依文件类型和内核版本而异。`ulimit -n` 显示当前 shell 的进程级文件描述符软限制，不是整个系统的上限。

### 观察 Linux 内核缓存

在 Linux 上可使用以下命令查看**系统级**统计：

```bash
free -h
grep -E '^(MemAvailable|Buffers|Cached|Dirty|Writeback|SReclaimable):' /proc/meminfo
```

| 字段           | 含义                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| `MemAvailable` | 内核估算的可供新应用使用的内存，考虑了部分可回收缓存；不是单纯的空闲内存。 |
| `Buffers`      | 与块设备缓冲相关的内存统计，不是程序的用户态缓冲区总量。                   |
| `Cached`       | 页缓存相关统计；不是全部内核缓存，也不等同于单个进程的文件缓存。           |
| `Dirty`        | 已修改、等待写回的内存。                                                   |
| `Writeback`    | 正在写回的内存。                                                           |
| `SReclaimable` | 可回收的 slab 内存，例如部分目录项和 inode 缓存。                          |

`free` 中的 `buff/cache` 是工具根据内核统计汇总的指标，不应简单理解为 `Buffers + Cached`；具体计算与 `free` 版本有关。这些数值是系统运行时的快照，会随其他进程和内核活动变化；不能用一次采样精确归因于某个排序任务。

### 对外部排序的影响

1 TB 的输入和输出不需要同时驻留在 32 GB 内存中。顺序读取的页缓存可以被回收并复用；输出对应的脏页需要先写回，才能作为干净页被回收。如果写入速度超过存储设备的持续写入速度，脏页积累后可能触发写入节流，降低排序速度。

生成和归并 run 时，缓存可能被其他数据替换；第二阶段不能假设所有临时数据仍在内存中。内存预算既要考虑排序数据和程序缓冲区，也要为内核及系统留出余量。上文约 4 TB 的 I/O 是按文件层面的逻辑读取和写入估算的，实际设备 I/O 还受页缓存命中、写回及文件系统等因素影响。

**程序刷新缓冲区、写入调用返回或关闭文件，都不等于数据已经可靠落到物理磁盘。**如果需要确认数据持久化，应先刷新用户态缓冲区，再根据可靠性要求调用 `fsync()` 等机制，并检查刷新、同步和关闭时的错误。普通文件 I/O 通常经过页缓存；例如使用 `O_DIRECT` 时，数据路径和约束有所不同。

### 对照：程序级缓冲区

程序或其使用的库在用户态内存中分配缓冲区，并决定何时读取或写入。例如，归并时可以为每个 run 分配一个输入缓冲区：程序先从缓冲区取记录，数据不足时再调用 `read()` 补充。输出时，程序先将结果放入输出缓冲区，缓冲区满后通过 `write()` 等接口写入文件，再复用该缓冲区。

这层缓冲区的大小和使用方式由程序或库控制，计入进程的内存占用。它可以减少系统调用次数，但不是每个程序都必须使用：程序也可以直接调用 `read()` 和 `write()`。对于变长记录，程序还要处理跨缓冲区边界的记录。

#### Python 示例

下面的程序对同一个文件提供两种读取模式：`buffered` 使用 Python 的 4 MiB 用户态缓冲区，`unbuffered` 不使用 Python 文件对象的额外缓冲。两种模式都每次向应用返回最多 4 KiB 数据，并计算 SHA-256，以便确认读到的内容一致。它**不是排序程序**。

```python
import argparse
import hashlib

BUFFER_SIZE = 4 * 1024 * 1024  # Python 文件缓冲区：4 MiB
CHUNK_SIZE = 4 * 1024          # 每次交给应用处理的数据：4 KiB


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("mode", choices=("buffered", "unbuffered"))
    parser.add_argument("path", help="要读取的文件")
    args = parser.parse_args()

    buffer_size = BUFFER_SIZE if args.mode == "buffered" else 0
    digest = hashlib.sha256()
    total = 0

    with open(args.path, "rb", buffering=buffer_size) as source:
        while True:
            chunk = source.read(CHUNK_SIZE)
            if not chunk:
                break
            digest.update(chunk)
            total += len(chunk)

    print(f"模式: {args.mode}")
    print(f"读取字节数: {total}")
    print(f"SHA-256: {digest.hexdigest()}")


if __name__ == "__main__":
    main()
```

将代码保存为 `buffer_example.py`，在 Linux 上对同一个文件分别运行：

```bash
python3 buffer_example.py buffered input.dat
python3 buffer_example.py unbuffered input.dat
```

两次运行读取的字节数和 SHA-256 应一致，前提是文件内容在两次运行之间没有变化。两种方式的区别是：

- **`buffered`**：`open(..., buffering=BUFFER_SIZE)` 使用 Python 管理的用户态缓冲区。调用 `source.read(4096)` 时，Python 可以从缓冲区返回数据；缓冲区不足时再向内核读取更多数据。多次应用层读取因此可能合并为较少的底层读取调用。
- **`unbuffered`**：`open(..., buffering=0)` 返回无额外 Python 文件缓冲的二进制文件对象。每次 `source.read(4096)` 都请求底层读取，而不是先从 Python 文件对象的缓冲区取数据。返回的 `chunk` 本身仍占用用户态内存；无缓冲不代表不使用任何内存。

**两种模式通常都会经过 Linux 内核页缓存**。这里的“直接读取”是指不使用 Python 文件对象的额外缓冲，**不是**绕过内核页缓存、直接从物理磁盘读取，也不是 `O_DIRECT`。内核仍可能命中缓存或进行预读；两次运行的缓存状态也可能不同，因此不能仅凭运行时间公平地比较两种模式。

实际归并中，每个 run 可使用独立的有缓冲文件对象，并从中解析记录；记录可能跨越底层读取边界。最终输出也可使用有缓冲的二进制文件对象，但刷新 Python 缓冲区仍不等于持久化到磁盘。

#### 在 `/proc` 中观察

程序级缓冲区只是进程虚拟地址空间中的一块内存，可能位于堆、匿名映射或其他内存区域。Linux 并不知道程序将哪块内存用作排序输入或输出缓冲区，因此 `/proc` 通常只能帮助观察进程及内存区域的使用情况，不能直接标识某个具体的程序缓冲区。

- `/proc/<pid>/status`：查看进程整体内存统计，例如 `VmSize` 和 `VmRSS`。
- `/proc/<pid>/maps`：查看虚拟内存区域及权限，例如 `[heap]` 和匿名映射。
- `/proc/<pid>/smaps`：查看各内存区域的详细统计，例如 `Size` 和 `Rss`。
- `/proc/<pid>/fd`：查看打开的文件描述符，但不能直接看到程序为文件分配的缓冲区。

例如，将下面命令中的 `<pid>` 替换为进程 ID：

```bash
grep -E 'VmSize|VmRSS' /proc/<pid>/status
cat /proc/<pid>/maps
```

不能仅凭某块内存属于堆或匿名映射，就断定它是排序缓冲区：同一区域还可能包含其他对象。要准确定位，可由程序提供缓冲区指标，或使用调试器查看变量地址及内存分析工具。
